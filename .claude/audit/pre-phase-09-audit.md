## 1. Method and evidence standard

**Sources consulted, in this order:**

1. `CLAUDE.md`, `DATABASE.md`, `.claude/plan/README.md` — read in full.
2. Every `README.md` and task document under `.claude/plan/phase-00-*` … `phase-08-*` —
   254 files, ~1.87 MB — but **not all at the same depth, and the difference matters to Step 2**:

   | Depth                                                                                                                               | Where                                                       |
   | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
   | Every section, verbatim                                                                                                             | All of P00; P01 `db-package-scaffold` and `identity-schema` |
   | Header table · `Depends on` · `Blocks` · `Scope` · `Files` · `Acceptance criteria` · `Verification` · `Risks` · implementer `Notes` | P01's other six features, and all of P02–P08                |

   What that second row **omits** is each task's `Why this exists` and `Approach` prose. Those
   sections are mostly rationale, but `Approach` occasionally carries a design decision that
   appears nowhere else in the document. Step 2 should re-read `Approach` for any task it
   scrutinises in depth rather than treating this audit as having covered it.

3. `git log`, `git branch -r --merged main`, and per-commit inspection.
4. The working tree: `git ls-files` inventories per workspace (1,044 tracked source files),
   plus targeted reads of the implementation, migrations, and tests each task names.

**Status vocabulary:**

| Status                  | Means                                                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅ Verified             | Code **and** tests exist on `main` and plausibly satisfy the acceptance criteria. Step 2 confirms depth.                                          |
| ✅ Verified (code side) | Same, but a material share of the task's criteria are physical-device measurements that no repository inspection can settle. Used throughout P04. |
| ⚠️ Partial              | Some acceptance criteria have matching implementation, others do not.                                                                             |
| ❌ Missing              | No implementation found on `main`.                                                                                                                |
| 🟡 Doc-only             | The task document describes something with no corresponding code.                                                                                 |
| 🔵 Undocumented         | Code or behaviour exists on `main` that no phase-00–08 task document covers.                                                                      |

**Evidence standard.** A row is ✅ only when the Evidence column names a concrete artefact — a
file path, a line number, a specific assertion inside a named test, a migration number, or a
commit hash. "A test file with a plausible name exists" was scored ⚠️, not ✅.

**Depth disclaimer.** Step 1 is an inventory pass. It establishes that the named artefacts exist
and that their content is on-topic for the acceptance criteria. It does **not** attempt to prove
correctness, concurrency-safety, or security — that is Steps 2 and 3. Where a row says a test
asserts something, the assertion text was read; where it says a file exists, only existence and
shape were checked.

**Branch state at audit time.** Every `feat/phase*` and `feature/*` branch for phases 00–08 is
merged into `main` (47 remote branches; `git branch -r --no-merged main` returns only
`origin/dependabot/npm_and_yarn/pnpm-dependencies-b0acc8b5e7`). One **local-only** commit was
found that never reached `origin` or `main` — see the P03 `invites` row.

**The headline.** Phases 00–08 are, with two exceptions, genuinely built and genuinely tested.
`pnpm check` on a serialised run is green across all 23 turbo tasks — 283 suites, 3,603 tests.
The plan tree's own verification notes are unusually honest: several tasks record real bugs
found and fixed during their own verification step, and at least three record deliberate,
reasoned deviations from `DATABASE.md` or `CLAUDE.md` that were then written back into those
documents. That is the behaviour you want and it is visible throughout P01 and P03.

**What is actually wrong** falls into three groups: two recurring jobs that exist but are never
scheduled; a handful of packaging and single-import invariants that hold only because of pnpm
hoisting; and a broad, systemic staleness in the plan tree itself, which no longer describes the
repository accurately enough to be navigated from.

### 2.2 Risk register for Step 2/3

Ordered by consequence, not by phase.

**R1 — Two compliance-facing recurring jobs are written but never run.**
`apps/api/src/worker.ts:96` installs exactly one repeatable trigger, `scheduleWeeklyExerciseReconcile()`.
`runAgeSweep` (`jobs/age-sweep.ts:17`, whose own comment reads _"Not yet wired to a BullMQ queue
or a cron trigger"_) and `sweepDeletionRequests` (`jobs/sweep-deletion-requests.ts:30`) have no
caller. Consequences on `main` today: **§21.5's daily minor→adult sweep never fires**, so a
17-year-old client stays `is_minor` and guardian-gated past their 18th birthday, and
`suspended_until` never expires; **§21.4's 7-day deletion grace never becomes a purge**, because
nothing finds the due `deletion_requests` rows. Both are legally-framed commitments. Step 2 should
decide whether this blocks P09 or is simply the next task after it.

**R2 — Undeclared runtime dependencies that only resolve because of `nodeLinker: hoisted`.**
`apps/mobile` value-imports `drizzle-orm` at 31 sites (including `src/db/client.ts:1-2`) and
`@trpc/server/observable` at `features/auth/refresh-interceptor.ts:2`, with neither in its
manifest. `packages/ui` imports `expo-image` (`Avatar.tsx`), `@gorhom/bottom-sheet` (`Sheet.tsx`),
and `react-native-safe-area-context` (`SheetFooter.tsx`) with none of the three in its `peerDependencies`
or `devDependencies` — directly against P00 `shared-config/04`'s peer-dependency discipline.
These work today and break the day the linker changes or `packages/ui` is consumed from anywhere
but this workspace. Cheap to fix; worth fixing before P09 adds more surface.

**R3 — The authorization allowlist contradicts its own governing task.**
P02 `authorization-middleware/05`'s acceptance criteria state _"Invite acceptance is **not** on
the list."_ `invites.accept` is on it, added by P03 `invites/04`, with a written and superficially
reasonable justification. `invites.confirmGuardianConsent` was added the same way by P07. Neither
addition updated the task that forbids them. Step 3 should decide which document is wrong — and
re-read the whole 12-entry allowlist and the 7-entry `NON_RESOURCE_ID_FIELDS` escape hatch, since
those two lists are the only ways to opt out of the enumeration test.

**R4 — All four transactional aggregate helpers are still stubs, and P09 needs two of them.**
`packages/db/src/aggregates/recompute-daily-summary.ts:5` — _"This stub proves the transactional
SHAPE only"_; `recompute-personal-records.ts:5` — _"Deliberately empty"_. `recomputeSessionVolume`
and `recomputePersonalRecords` are direct dependencies of P09's `session-summary` and
`personal-records` features. Correct per P01's own scope, but it means P09 opens by implementing
DB§8.2's invariants, not by consuming them. Only one of the four has a test.

**R5 — `pnpm check` fails under parallel execution on this machine, and passes serially.**
A forced parallel run failed `@coachos/db#test` with a 60-second testcontainer `beforeAll`
timeout while `api:test` was concurrently spinning up its own Postgres containers. The same
command with `--concurrency=1` passed 23/23. CI runs the parallel form. This is a flake with a
real cause (Docker contention), not a defect — but it will fail CI intermittently, and a flaky
gate erodes into an ignored gate.

**R6 — Three custom ESLint rules that encode product law have no tests.**
`no-raw-color`, `adherence-colors-only`, and `no-arbitrary-tailwind` (P04 `theme-tokens/05`) and
`no-hand-written-row-type` (P01 `db-package-scaffold/05`) are all registered as `error` and all
untested. P04 `theme-tokens/05`'s own Files table names a `rules.test.js` that was never created.
Only `no-bare-invalidate-queries` and `no-direct-outbox-write` have tests. A lint rule that
silently stops matching is indistinguishable from a clean codebase — and these four are what keep
raw hex, arbitrary Tailwind values, and hand-written row types out.

**R7 — `packages/config` reaches into `packages/ui` through a relative path.**
`packages/config/tailwind/preset.js` does `require('../../ui/src/theme/tokens.ts')` and
`require('../../ui/src/theme/to-rgb-channels.ts')`. That is (a) a relative import crossing a
workspace boundary, which P00 `shared-config/01`'s own AC says must be an ESLint error; (b) an
undeclared `packages/config → packages/ui` dependency; and (c) an inversion of the intended
direction, since `packages/ui` extends `packages/config`. P00 `shared-config/01` also states
"do not let `packages/config` acquire runtime code."

**R8 — Finished settings UI that no screen renders.**
`UnitRow.tsx` (P03 `account-lifecycle/08`) and `AppearanceRow.tsx` are built and tested;
`YourDataScreen.tsx` is routed at `/your-data` but linked from nowhere. Both settings screens are
still P05 placeholders rendering their own route path plus one disclaimer link. Three finished
acceptance criteria — "switching units is instant", "reachable in ≤2 taps from settings" — are
not true from a user's point of view. No task before P09 owns the real settings screen.

**R9 — Seven user-facing error strings sit on an unmerged local branch.**
`feat/phase3-invites` carries `7934f56`, _"align invite error copy with the local ERRORS.md
catalogue"_, which is on neither `main` nor `origin`. `main` still throws
`'This invite code is not valid.'` where ERRORS.md ER§1.9 specifies different copy, and
`seat-check.ts` still uses a static `SEAT_LIMIT_MESSAGE` where ER§1.3 specifies a
seat-count-interpolated template. The work is done; it was never pushed.

**R10 — The migration CI idempotency step cannot fail for the reason it exists.**
`.github/workflows/migrations.yml`'s "Apply migrations again (must be a no-op)" step re-runs
`db:migrate`, which consults its own bookkeeping table and exits 0 without re-executing anything.
The task doc records the caveat honestly and explains why forcing raw re-execution would break on
`CREATE TYPE`. Still: DB§12.1 point 5's check is currently a tautology. Step 2 should decide
whether a real check is worth building.

**R11 — Only 3 of 10 declared BullMQ queues have a `Worker`,** and the registry disagrees with
DB§15: `account-deletion` is in the code and not in DB§15; DB§15's `age-and-moderation-sweep` and
`nutrition-reconcile` are in the document and not in the code. `nutrition-reconcile` is
legitimately P13's. The other two are drift, and one of them is R1.

**Refresh rotation and reuse detection, read assertion by assertion.** `__tests__/auth-refresh.test.ts`:

- `:71` rotation revokes the presented token, chains `replaced_by`, and keeps `family_id` and
  `device_id` — asserted on the actual rows, plus `successor.expiresAt > before.expiresAt`.
- `:104` walks **five** consecutive rotations and asserts `familyIds.size === 1`, exactly one live

- `:130` is the reuse case and it proves the whole property, not a fragment: after a legitimate
  rotation the consumed token is backdated past the grace window, re-presented, and rejected
  `UNAUTHORIZED`; then **every** row in the family is asserted revoked; then **the legitimate
  successor is asserted dead too** (family invalidation, which is the part a weak test would skip);
  then an `auth.refresh.reuse` `audit_log` row is asserted present.
- `:174`–`:210` are three "touch nothing" cases — an unknown token creates and revokes nothing, an
  expired token leaves `revokedAt` null, and a revoked family cannot refresh.

up**: it fires two `auth.refresh` calls with the same token through `Promise.allSettled` and
asserts exactly one fulfilled, exactly one rejected with `CONFLICT`, exactly one live token left
(family alive), and — the discriminating assertion — **zero `auth.refresh.reuse` audit rows**. A
race must not be punished as theft.

> **Design nuance worth recording, not a defect.** `rotate-refresh-token.ts:24`
> `REUSE_GRACE_WINDOW_MS = 10 * 1000`. A token re-presented within 10 seconds of its own rotation is
> classified `REFRESH_RACE`, **not** reuse, and does not revoke the family. That is the standard
> trade for a mobile client on a bad connection, and the race test above is what it buys; but it
> means a stolen refresh token replayed inside that window is not detected. Recorded so the
> trade-off is visible rather than implicit.

**The client-local date guarantee, precisely.** The AC asks for it to be _"verified across a
timezone boundary"_. No such test exists, and none is needed, because the implementation
**removed the boundary rather than testing across it**: `lib/materialise-sessions.ts:63-66`
records that `assignments.start_date` and `workout_sessions.scheduled_date` are both `date`
columns holding client-local calendar days already, so _"there is no UTC instant anywhere in the
walk"_. `calendarDateForProgramDay` is therefore pure calendar arithmetic, and its test proves
that shape instead — including `:214` _"spans a DST transition as pure calendar arithmetic, with
no shift"_ across the 2026 US spring-forward Sunday, explicitly with no timezone argument. The
`date`-column choice was independently confirmed against the **live catalogue** in §8.1. The
remaining human input, the coach's chosen start date, defaults to the coach's own device day and
is documented at `AssignProgramSheet.tsx:105-108` as a picker default the coach can change rather
than an inferred day boundary. **Stronger than the AC asked for; different from what it describes.**

**Three facts P09 must not re-derive** (all established here, all verified this pass):

1. **`program_snapshot` is deliberately `null` at materialisation.** `materialise-sessions.ts:58`:
   DB§14.6 defines it as _"the prescription frozen at START, written only when a client actually
   starts a session, never at scheduling time."_ A grep for `programSnapshot` across `apps/api/src`
   excluding tests returns **only comments** — **nothing on `main` writes it. P09 owns that write.**
2. **A materialised session is a shell.** No target, prescription, or even the day's `name` is
   copied onto it; everything resolves live through `program_day_id`. `total_volume_kg` also stays
   null (see **F6** — the recompute stub would write `'0'`, not the real sum).
3. **The live-reference model is proven, both directions.**
   `routers/__tests__/assignments.bulk-edit.test.ts:243-247` — after a template edit, future sessions
   are still `scheduled` and the live target reads the **new** value (3 → 5); `:282`
   `expect(rows).toEqual([sessionsBefore[index]])` — the session rows are byte-identical, untouched;
   `:289` _"does not change set_logs or the frozen program_snapshot of an already-completed
   session"_, asserting both the snapshot and `{ reps: 8, weightKg: '60.00' }` survive.
   Ammar confirmed live-reference on 2026-09-08; `CLAUDE.md` §27's open entry is closed in fix **X3**.
